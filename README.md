# ВышКат — учёт парка кикшеринга

Домашнее задание № 1

«ВышКат» — консольное приложение для учёта транспортных средств и вещей. Цель проекта — реализовать простую доменную модель с использованием ООП, принципов SOLID, Dependency Injection и автоматизированных тестов.

## Возможности

- Добавление велосипеда, самоката и электровелосипеда с обязательным техосмотром.
- Отклонение транспорта, не прошедшего техосмотр.
- Регистрация шлемов, док-станций и зарядных шкафов без техосмотра.
- Учёт количества транспорта, вещей и общего числа инвентарных объектов.
- Расчёт суммарного энергопотребления зарегистрированных объектов.
- Отбор принятого транспорта для новичков по правилу `ease >= 6`.
- Просмотр наименований и инвентарных номеров всего парка.
- Обработка некорректного пользовательского ввода и повторяющихся инвентарных номеров.

## Установка и запуск

Требуется **Python 3.10+** (используются аннотации `list[Technic]` и `dict[str, Technic]`).

Перейдите в каталог `task1`, содержащий `main.py` и `requirements.txt`, и выполните:

```bash

```

- `pytest` — запуск тестов;

## Использование консоли

После запуска `python main.py` отображается меню:

```text
1. Добавить транспорт
2. Добавить вещь
3. Показать количество объектов
4. Показать энергопотребление
5. Показать транспорт для новичков
6. Показать весь инвентарь
0. Выход
```

При добавлении транспорта пользователь выбирает его вид, задаёт инвентарный номер, название, простоту управления от 1 до 10 и состояние (`да`/`нет`). Для самоката и электровелосипеда дополнительно вводится энергопотребление. Для вещей вводятся номер и название, а для док станции и зарядного шкафа - также энергопотребление.

Выход — пункт `0`. `Ctrl+C` или завершение стандартного ввода также обрабатываются в основном цикле приложения.

## Доменная модель и правила

### Инвентаризация

`InventoryItem` реализует `IInventoryItem` и хранит `inventory_number` и `name`. Эти значения должны быть непустыми строками. Публичных сеттеров для изменения номера и названия нет.

Все объекты транспорта (`Technic`) и вещи (`Thing`) наследуют общие инвентарные свойства. `Park` хранит транспорт и вещи в отдельных словарях и через `_check_free_number()` обеспечивает уникальность номеров между обеими категориями. Повторный номер вызывает `ValueError`.

### Техосмотр и транспорт для новичков

`Park.success_technic()` сначала проверяет уникальность номера, затем вызывает `IInspector.check()`. Если инспектор возвращает `False`, транспорт не регистрируется. В проекте реальная реализация `ServiceCenter.check()` возвращает значение `technic.is_check`, переданное при создании объекта: это упрощённая модель техосмотра, а не настоящая диагностика.

Для транспорта значение `ease` должно быть целым числом от 1 до 10; `bool` в качестве `ease` запрещён. `Park.technics_beginner()` возвращает только зарегистрированный транспорт, у которого `ease >= 6`. Отклонённые экземпляры туда не попадают.

### Энергопотребление

`IEnergyConsumer` объявляет свойство `energy_use`. Его реализуют `ElectricTechnic` (в том числе `Samokat`, `ElectricBike`) и `ThingPowered` (в том числе `DockStation`, `ChargeWardrobe`). Обычные `Bike` и `Helmet` это свойство не имеют.

`Park.general_energy_use()` суммирует `energy_use` только тех объектов, которые находятся в парке и реализуют `IEnergyConsumer`. Поэтому неэнергопотребляющие и отклонённые объекты не увеличивают отчёт.

## SOLID: решения и обоснование

- **S — Single Responsibility Principle.** `InventoryItem` отвечает за общие инвентарные данные и их валидацию, `ServiceCenter` — за решение техосмотра, `main.py` — за взаимодействие с пользователем. `Park` сосредоточен на операциях с парком: регистрации и отчётах. Мы не выносим каждую операцию в отдельный сервис, поскольку проект небольшой.
- **O — Open/Closed Principle.** Новые подвиды транспорта можно добавлять через наследование от `Technic` или `ElectricTechnic`; базовые алгоритмы приёмки, учёта и энергопотребления в `Park` менять не нужно. При этом меню `main.py` содержит явный выбор конкретных видов, поэтому для добавления нового пункта меню его придётся изменить. Это сознательное ограничение расширяемости интерфейса.
- **L — Liskov Substitution Principle.** `Bike`, `Samokat` и `ElectricBike` используют общий контракт `Technic` (`inventory_number`, `name`, `ease`, `is_check`) и передаются в `Park.success_technic()` одинаковым образом. Энергопотребляющие подтипы дополнительно реализуют `IEnergyConsumer`.
- **I — Interface Segregation Principle.** `IInventoryItem`, `IEnergyConsumer` и `IInspector` имеют разные узкие обязанности. Например, `Helmet` не обязан реализовывать `energy_use`, а транспорт не обязан предоставлять методы техосмотра — это ответственность инспектора.
- **D — Dependency Inversion Principle.** `Park` зависит от абстракции `IInspector`, а не от `ServiceCenter`: `Park.__init__(self, inspector: IInspector)`. Конкретная реализация внедряется извне. `hsekat/container.py` регистрирует `IInspector -> ServiceCenter` в `punq` и создаёт `Park` через `container.resolve(Park)`.

### Наиболее явно применённый принцип

**DIP**: код `Park` не создаёт `ServiceCenter` самостоятельно. Это позволяет использовать настоящий сервис в `main.py` и `demo.py`, а в тестах передавать `FakeInspector` без изменения `Park`.

### Какой принцип сознательно ограничен

**OCP применён не полностью на уровне консольного интерфейса.** При добавлении нового вида транспорта требуется добавить ветку выбора в `main.py`, хотя `Park` и интерфейсы менять не нужно. Для учебного приложения с тремя видами транспорта это проще и понятнее, чем дополнительный реестр фабрик или сложная система плагинов. Расширение меню — известная точка изменения, а не случайная зависимость бизнес-логики от конкретного класса.

Дополнительно в `Park` объединены приёмка, регистрация и агрегированные отчёты; мы сохраняем эту ответственность цельной, поскольку речь идёт об управлении небольшим парком. При росте системы отчёты можно выделить отдельно.

## Как можно расширить проект

**Новый вид транспорта.** Можно создать новый класс-наследник `Technic` (или `ElectricTechnic`, если он потребляет энергию). `Park.success_technic()`, `technics_beginner()` и подсчёт энергии продолжат работать по общим контрактам. Чтобы пользователь мог выбрать новый тип в консоли, потребуется добавить вариант в `main.py`.

**Сотрудники эксплуатации.** Сотрудники по условию не ставятся на баланс. Для их учёта можно создать отдельную модель и сервис сотрудников. Добавлять сотрудников в `Park.all_inventory()` не нужно; существующая инвентаризация сохраняет смысл.

**Склад запчастей.** Для нового склада логично добавить отдельный компонент учёта остатков. Если запчасти нужно инвентаризировать поштучно, можно использовать `IInventoryItem`; если ведётся количественный складской учёт, потребуется отдельная модель запасов. Сейчас `Park` не является системой управления складом.

## Dependency Injection и тестирование

В `hsekat/container.py` зарегистрированы:

```python
container.register(IInspector, ServiceCenter)
container.register(Park)
```

В `main.py` и `demo.py` объект парка получается из контейнера:

```python
container = create_container()
park = container.resolve(Park)
```

Для модульных тестов `Park` используется внедрение через конструктор без контейнера:

```python
inspector = FakeInspector(False)
park = Park(inspector)
```

`FakeInspector` определён в `tests/test_park.py`. Он реализует `IInspector`, возвращает заранее установленный `True` или `False` и записывает переданные объекты в список `checked`. Это позволяет независимо от `technic.is_check` проверить, что парк принимает решение по ответу инспектора и действительно вызывает его. Контейнер при этом не нужен для каждого отдельного юнит-теста: он проверяется отдельно в `tests/test_container.py`.

Ключевые тесты:

| Файл / тест | Что проверяет |
| --- | --- |
| `tests/test_park.py::test_fake_add` | При положительном результате фейкового техосмотра транспорт принимается, даже если `is_check=False` |
| `tests/test_park.py::test_fake_not_add` | При отказе транспорт не добавляется и не учитывается в энергии |
| `tests/test_park.py::test_thing` | Регистрация шлема не вызывает техосмотр |
| `tests/test_park.py::test_duplicate` | Повторный инвентарный номер между категориями запрещён |
| `tests/test_park.py::test_technics_beginner` | Для новичков допускается только принятая техника с `ease >= 6` |
| `tests/test_park.py::test_few_technic_thing` | Энергия суммируется для электротранспорта и энергопотребляющих вещей |
| `tests/test_inspector.py::test_inspector` | Настоящий `ServiceCenter` возвращает состояние техники |
| `tests/test_container.py::test_container` | Контейнер способен создать работающий `Park` |
| `tests/test_models.py` | Проверка типов, диапазонов значений и базовых контрактов моделей |

Тесты запускаются из корня проекта:

```bash
python -m pytest -v
```

Отчёт по покрытию:

```bash
python -m pytest --cov=hsekat --cov-report=term-missing
```

Ориентир из задания — покрытие **не менее 60%**. При проверке модели и логики парка без теста `test_container.py` проходили **36 тестовых случаев** с покрытием пакета `hsekat` **91%**

## Ограничения текущей реализации

- Данные хранятся в памяти: при перезапуске приложения парк создаётся заново. База данных и сохранение в файлы не реализованы, поскольку этого нет в требованиях.
- Техосмотр упрощён: `ServiceCenter` использует `is_check`, а не измерения или внешнюю систему диагностики.
- Новичками считаются пользователи, которым можно выдавать принятый транспорт с `ease >= 6`; дополнительных ограничений по скорости, возрасту или состоянию батареи нет.
- `Park.all_inventory()` возвращает сначала транспорт, затем вещи, а не общий хронологический порядок их добавления.
- Меню явно перечисляет поддерживаемые типы объектов; добавление новых пунктов требует изменения `main.py`.
